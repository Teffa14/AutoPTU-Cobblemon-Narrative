# Ouros Temporary Event Operations Seeds — Pass 55

Status: PROPOSED. Non-canon until reviewed.

These candidates use the Pass-55 temporary-event operations extension. Names, institutions, locations, traditions and technology remain provisional. They do not establish Ouros canon.

## 1. Lanternmarket Opening Hour

Type: operational social quest.

Premise:
A temporary evening market is due to open, but three dependencies are degraded at once: one vendor delivery is late, a planned public access route is unavailable, and an information board still shows the old site layout.

The players are involved because they have an authored role with one host, vendor, local institution or volunteer group. They do not automatically gain authority over the event.

Playable structure:
- inspect the actual dependency state;
- identify which failures can be solved before opening;
- choose whether to delay, open limited, relocate one service or leave one activity closed;
- communicate the resulting program accurately;
- allow the event to proceed with visible consequences.

Persistent outputs:
- event-instance opening decision;
- vendor/service availability;
- updated information packet;
- Chronicle record of who solved what;
- next-edition change candidate if the access problem was structural.

No combat required.

Canon questions:
- which settlement could support this event;
- whether the event name fits local culture;
- what institution has opening authority;
- which temporary services are plausible there.

## 2. The Wrong-Side Queue

Type: public-space problem.

Premise:
One popular event activity draws far more visitors than expected. Its queue begins interfering with another legitimate use of the same location, such as a clinic access path, transport entrance, resident route, quiet area or ecologically restricted edge.

The conflict should come from actual site and visitor state. The generator must not invent congestion only to create a quest.

Possible responses:
- move the queue;
- temporarily limit entry;
- add a second access point if the site supports it;
- alter the activity schedule;
- pause the activity;
- communicate a changed route.

Persistent outputs:
- new temporary site flow;
- participant satisfaction/public-memory claim, if observed;
- accessibility or service impact;
- next-edition site-plan note.

Mechanical boundary:
Crowd pressure remains world state. It does not create difficult terrain, forced movement or Accuracy penalties.

## 3. Last Vendor Out

Type: teardown mystery / custody hook.

Premise:
After most of a temporary market has packed up, staff find one sealed crate or equipment case whose custody record does not match the final vendor roster.

The object may be:
- borrowed event equipment;
- ordinary stock delivered to the wrong stall;
- a historical display item awaiting return;
- lost property;
- case-relevant evidence only if the Case layer supplies that status;
- something mundane whose owner simply left early.

The quest begins from a custody inconsistency, not from assuming theft.

Playable structure:
- reconstruct the temporary service roster;
- compare delivery/provenance records;
- contact plausible custodians through valid channels;
- decide whether the item stays secured, is returned or is handed to an institution with established authority.

Persistent outputs:
- provenance/custody event;
- possible recurring vendor contact;
- event closure handoff;
- corrected teardown procedure for a future edition.

No invented legal powers, prices or item mechanics.

## 4. Rain Plan B

Type: event relocation / service-state problem.

Premise:
Observed weather makes part of an outdoor public event unsuitable shortly before or during operation. The host has an authored fallback plan, but moving every activity would exceed available indoor or sheltered space.

The players may help assess priorities if their relationship/role makes that plausible.

Playable structure:
- verify observed weather and actual site state;
- query which activities can relocate without changing their mechanics;
- preserve accessibility and service dependencies;
- choose which activities continue, pause or move;
- issue corrections to the public schedule;
- record what the next edition should prepare differently.

Full combat version:
If an unrelated threat occurs while weather, temporary structures and evacuation are tactically active, the concept would require terrain/weather/hazards/zones/reactions, complete movement, lifecycle support, tactical AI and adapter/playback. Those families are not currently ready.

Reduced version:
Resolve relocation and public movement entirely in overworld state. If combat occurs, clear visitors first and instantiate a static legal arena with no weather-derived tactical modifier unless AutoPTU explicitly supports the exact mechanic.

## 5. Edition Memory Dispute

Type: cultural / archival investigation.

Premise:
A recurring event is preparing a commemorative display. An archive, family record, archaeological observation or prior edition photograph conflicts with a popular caption that has been repeated for years.

The conflict concerns what the event publicly says, not whether the event itself should exist.

Playable structure:
- identify the claim in dispute;
- separate archival evidence, testimony, tradition and canonical world truth;
- interview or consult relevant actors without fabricating private beliefs;
- let the host decide whether to preserve, qualify or correct the display;
- publish any revision through the communication layer;
- preserve the old edition in public-memory history.

Persistent outputs:
- information revision;
- public-memory entry;
- possible institutional disagreement;
- changed display state for this and future editions.

No supernatural or Legendary conclusion should be generated from cultural tradition alone.

## 6. Cleanup Shift, Wildlife Return

Type: ecological aftermath.

Premise:
A public event used a location that is normally shared with wild Pokémon. During teardown, observation shows the animals returning earlier or in greater numbers than expected, while equipment and cleanup crews still occupy part of the area.

Noncombat path:
- pause teardown in the affected zone;
- observe behavior and compare with prior ecology records;
- move equipment if feasible;
- adjust cleanup order;
- hand findings to conservation/research owners;
- reopen the site only when the real operational state supports it.

Full tactical version:
Dynamic occupied zones, territorial withdrawal behavior, reactions, changing equipment hazards and objective-aware AI would depend on BLOCKING capability families.

Reduced combat version:
Remove staff and visitors before battle. Use a fixed perimeter arena containing only legal combatants. Do not grant territorial bonuses or simulate moving cleanup equipment. Resume teardown after authoritative battle result handoff.

Persistent outputs:
- ecological observation;
- cleanup delay;
- next-edition habitat-use note;
- potential recurring research question.

## 7. The Activity That Does Not Open

Type: expectation / relationship scene.

Premise:
A performer, instructor, artisan or activity operator cannot open their scheduled event activity. The reason may be illness, missing equipment, a family obligation, a supply failure, a damaged workspace or another authored constraint.

The story should not default to replacing the person or making the player perform a job they are not qualified to do.

Possible responses:
- cancel honestly;
- reschedule;
- convert the slot to a non-mechanical demonstration only if the operator approves;
- help solve the external blocker;
- preserve the relationship for a future edition.

Persistent outputs:
- activity availability state;
- operator relationship/Chronicle event;
- public schedule correction;
- next-edition follow-up.

No Trainer Feature, crafting recipe, performance mechanic or professional qualification is granted narratively.

## 8. Split Program

Type: event-planning choice.

Premise:
A temporary event has enough staffing and supplies for all planned activities across the full day, but a transport disruption means the largest visitor cohort will arrive late. The host must decide whether to preserve the original schedule or repeat selected activities later.

This creates a meaningful choice because repeating an activity may conflict with staff hours, cleanup, ecological restrictions or another site's use.

Playable structure:
- verify transit/service state;
- identify which activities can move within existing operator availability;
- compare consequences;
- publish the chosen program;
- record which cohort actually witnessed each activity.

Persistent outputs:
- event schedule revision;
- visitor cohort knowledge/experience differences;
- operator workload state only if Workplaces owns it;
- next-edition transport dependency note.

No assumed overtime policy, capacity number or compensation formula.

## 9. Encounter seed — Crowdline Breakout

Type: capability-aware public-event encounter.

Narrative premise:
A disturbance occurs next to an active event. The immediate objective is to get visitors out of the affected zone, then contain a small set of actual combatants.

Intended full version:

- pursuit/escape objectives;

## 10. Longer arc — An Event Learns

Type: recurring-edition continuity arc.

Edition 1:
The event runs with a workable but imperfect site plan. The party may observe access, queue, cleanup or delivery problems. Only actual incidents become records.

Between editions:
Host institutions review closure handoff, public-memory entries, service failures and ecological observations.

Edition 2:
The layout or schedule changes. Some changes solve earlier problems while creating different tradeoffs. Returning staff and visitors can recognize what changed.

Edition 3+:
The event develops stable traditions, discontinued practices, recurring vendors, known weak points, staff succession and public expectations. New stories emerge from accumulated state rather than replaying the same crisis.

Design goal:
A recurring public event should become a small persistent institution with memory. It should not require an emergency every year to remain interesting.

## 11. Canon review questions

Before promoting any seed:
- Which specific Ouros settlements or regions support temporary public events of this scale?
- Which existing institutions can host them?
- What calendar/cycle governs recurrence?
- Which event technologies, stalls, public-address systems and temporary structures fit established regional tech?
- What visitor volume can Minecraft represent without performance problems?
- Which activities already have PTU/Caelo or AutoPTU mechanical definitions?
- Which local Pokémon/ecology facts make shared-site pressure plausible?
- What authority governs closure, relocation, lost property and public-safety decisions?
- Which names and cultural motifs fit already approved Ouros lore?

Until answered, all names and scenarios in this file remain proposals.
